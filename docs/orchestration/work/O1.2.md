# O1.2 — Runner local mínimo, sin Claude real y sin push automático

**Autorizó:** Juan, en la conversación de Claude Code, con las decisiones 1 y 2 de O1.2-A y la
decisión 3 rediseñada. **Fecha:** 2026-11-01.

Este bloque se dirige a mano con el contrato de O1.1: el runner todavía no se usa para construirse
a sí mismo.

## Objetivo

Disponer de un runner local que valide una especificación aprobada, prepare una copia de trabajo
aparte, compruebe por Git lo que cambió un ejecutor falso, ejecute controles fijos, genere evidencia
sanitizada, haga commits solo locales y se detenga.

## Dentro del alcance

1. `scripts/orchestrator.py`: órdenes `validate`, `run`, `status` y `cleanup`.
2. `scripts/Start-ElsaBlock.ps1`: lanzador delgado.
3. `tests/fake_orchestrator_executor.py`: ejecutor falso, solo para pruebas.
4. Tests unitarios, de integración con Git local, solo de Windows y ensayo controlado.
5. `pyproject.toml`: solo para que mypy y pytest cubran `scripts/`, sin tocar dependencias.
6. Actualización de `docs/orchestration/README.md`.
7. Parte A: ensayo en repositorio desechable, antes del PR.
8. Parte B: `validate` de solo lectura en el repositorio real, después del merge.
9. `docs/o1-2-runner-local-minimo-cierre.md`, en un segundo PR.

## Fuera del alcance

- Claude real, `claude -p` y toda ejecución sin supervisión: O1.3.
- Publicar ramas, leer CI y generar el enlace del PR desde el runner: O1.4.
- El ajuste de la Skill `elsa-release`: O1.4.
- `src/elsa`, `CLAUDE.md`, `ci.yml`, `uv.lock`, `.env`, `.claude/`, Render, Supabase y SAP.
- El ADR 0036, salvo contradicción real.
- Una base de datos, dependencias nuevas o instalación de programas.

## Decisiones

| Decisión | Motivo |
|---|---|
| El runner no importa `elsa`, aunque repite patrones de `elsa.pc1` | O1 es tooling, no producto |
| `state\` guarda solo el lock | El ADR 0036 §4 prohíbe un archivo de estado aparte |
| El resultado de O1.2 es `verified_local`, sin estado nuevo | `PR_READY` exige publicar y O1.2 no publica |
| El ejecutor no puede commitear; los commits son del runner y solo locales | Lo escaneado es exactamente lo que entra. Aprobado por Juan |
| Los controles usan el `.venv` principal con `PYTHONPATH` apuntando a la copia | El runner no debe instalar librerías; un control verifica de dónde se carga `elsa` |
| La prueba real no crea ramas en el repositorio real | Aprobado por Juan: sin `git branch -D` |
| El control `mypy` usa `--platform linux`, como CI | `src/elsa/bench/runner.py` no tipa en Windows, y `src/elsa` queda fuera de este bloque |
| En Windows, `pytest` omite exactamente 3 pruebas que ya fallan sobre `main` limpio | Aprobado por Juan como excepción: lista fija, solo Windows, CI las sigue corriendo y cualquier otra falla detiene el bloque |

## Criterios de aceptación

| Acción | Resultado esperado |
|---|---|
| Escenarios del ejecutor falso | Cada uno termina con el código de motivo previsto |
| Timeout con hijo y nieto en Windows | No queda ningún proceso vivo |
| Comandos y argumentos de Git | Sin `push`, `merge`, `rebase`, `pull`, `reset`, `clean`, `--force`, `-D` ni `--no-verify` |
| Campo `commands` en la especificación | Rechazado |
| Parte A | Sin cambios y edición permitida: `verified_local`; token falso: `secret_detected`; repositorio real idéntico |
| Controles de cierre | pytest, ruff, mypy, pre-commit y `git diff --check` en verde |
| Rama publicada a mano, PR creado por Juan | CI en verde |
| Parte B, tras el merge | `validate` correcto; repositorio real idéntico |
| Merge de los dos PR por Juan | `main` limpio y sincronizado |

## Riesgos

| Riesgo | Mitigación |
|---|---|
| El ejecutor falso no prueba nada sobre Claude real | O1.3 sigue siendo el punto de decisión |
| Las fotos del repositorio detectan un abuso, pero no lo impiden | Riesgo de aislamiento, a decidir en O1.3 |
| `NtResumeProcess` no está documentada | Prueba repetida; si falla, se detiene y se reporta |
| La limpieza de logs es parcial | Los logs nunca se versionan; límite declarado |
| Un `.venv` desactualizado da un resultado engañoso | Control de origen de `elsa`; CI es la autoridad |

## Pruebas omitidas en Windows

| Prueba | Causa conocida |
|---|---|
| `tests/test_bench_harness.py::test_a_run_records_what_produced_it` | `_windows_peak_rss_mb` de `elsa.bench` devuelve `None` y la prueba exige una cifra |
| `tests/test_bench_harness.py::test_peak_memory_is_measured_where_the_posix_api_exists` | La prueba exige el módulo `resource`, que solo existe en POSIX |
| `tests/test_pc1_supervisor.py::test_a_real_ctrl_c_reaches_only_the_supervisor_which_stops_in_order` | Intermitente: compara con `<` dos marcas de reloj que en Windows pueden coincidir |

**Pendiente:** corregir esas causas en un bloque aparte, sin tocar `src/elsa` dentro de O1.2. Al
corregirlas, la lista `WINDOWS_KNOWN_TEST_FAILURES` del runner debe quedar vacía.
